# 웹 프리셋 편집기 결정 사항 및 구현 설계

> 작성일: 2026-09-08
> 상태: 공통 엔진 추출 완료 후 `feat/web-editor-host`에서 웹 호스트 구현 진행
> 이 문서는 결정의 변경 이력을 보존한다. 이전 추출 결과는 [공통 엔진 추출 기록](shared-editor-extraction.md), 현재 웹 구현과 검증은 [웹 호스트 구현 기록](web-editor-implementation.md)을 따른다.

## 1. 목적과 기준

DmNote 데스크톱 앱과 별도의 웹사이트에서 프리셋 디자인을 편집하고 내보낼 수 있도록 편집 엔진과 UI를 공유한다. 웹사이트에서 내보낸 프리셋은 데스크톱 앱에서 사용한다.

기능과 데이터 의미의 기준은 현재 앱이다. 웹 이식을 이유로 프리셋 포함 항목, 플러그인 저장 의미, 편집 결과를 별도로 재정의하지 않는다. 브라우저 제약으로 동일한 구현이 불가능한 부분은 호스트 구현으로 분리하고, 실제 동작 차이가 필요한 경우 개별적으로 논의한다.

이하에서 **확정**은 대화에서 합의한 방향, **제안**은 아직 선택하지 않은 구현안, **미정**은 후속 논의가 필요한 계약을 뜻한다.

### 1.1 이번 브랜치의 범위와 완료 기준

2026-09-09 사용자 확인: `feat/shared-editor-engine`의 목표는 **공유 가능한 편집 엔진·관련 공통 모듈을 분리하고 기존 앱에 연결해 기존 동작과 결과를 검증하는 것**이다. 웹사이트 완성까지를 이번 브랜치의 완료 조건으로 삼지 않는다.

이번 작업의 완료 기준:

- 공통 Rust 엔진과 공유 대상 TypeScript 코드의 모듈 경계를 분리하고, 네이티브 기능은 앱 호스트에 남긴다.
- 공통 모듈을 외부 소비자가 명시된 진입점으로 사용할 수 있도록 의존성·타입·필수 자산과 호스트 계약을 정리한다. 현재 앱의 내부 경로를 임의로 참조해야만 사용할 수 있는 상태를 완료로 보지 않는다.
- 기존 앱이 분리된 공통 모듈을 실제로 사용하도록 재연결한다. 앱의 별도 기존 로직만 계속 실행되는 상태에서 추출 완료로 판단하지 않는다.
- 편집·히스토리·프리셋·플러그인·저장 및 복구의 기존 동작과 결과를 검증하고, shim 공통화에 따른 OBS 회귀도 확인한다.
- Rust 공통 코드의 WASM 빌드 가능성과 브라우저용 호출 경계를 최소 검증한다. 전체 웹 제품 구현과 구분하며, 네이티브 의존성이 남아 추출 후 다시 대규모 분리가 필요한 상태를 방지하는 목적이다.
- 실제 검증 범위와 미검증 항목을 기록한다. 구현·검증 전에는 모든 동작이 동일하다고 선언하지 않는다.

후속 작업:

- 앱 연결과 검증이 끝난 뒤 공통 코드를 웹 개발 저장소에서 소비한다. 소스를 DmNote 저장소에 유지하면서 패키지로 배포할지, 별도 공통 저장소로 옮겨 배포할지는 아직 확정하지 않았다.
- SharedWorker 웹 호스트, IndexedDB 저장 구현, 웹 전용 화면과 기능 연결, CSS Worker 배포 및 사이트 배포는 후속 웹 개발에서 수행한다.
- 이 문서에 정한 웹 구조는 후속 개발의 설계 의도로 유지한다. 이번 추출에서는 그 구조에 연결할 수 있는 계약과 경계를 마련한다.
- 저장소는 소스를 관리하는 단위, Rust crate·TypeScript 패키지는 코드 소비 단위다. 현재 저장소 안에서 모듈·패키지 경계를 먼저 검증한 뒤 물리적인 저장소 이동을 진행할 수 있다. Git submodule 사용 여부는 별도 선택이다.

## 2. 확정된 결정

### 2026-09-09 후속 구현 범위 확정

사용자 확인: 공통 엔진과 웹 실행 엔진도 **DmNote 저장소 안에서 함께 구현·관리하고 패키지로 제공**한다. 웹 전용 저장소는 편집 화면·미리보기의 조립, 사이트 기능과 배포를 담당한다. 위 1.1의 후속 작업 목록은 이전 추출 브랜치가 끝난 시점의 기록이며, 웹 호스트를 별도 사이트 저장소에서 구현한다는 배치안은 이 결정으로 변경한다.

- `packages/web-host`에서 SharedWorker 세션, WASM 로딩, IndexedDB 저장, 브라우저 파일·입력·자산·소리·미리보기 어댑터를 제공한다.
- Rust의 웹 명령 세션·프리셋 자산 처리·키 매칭·미리보기 검증을 `src-tauri/crates/editor-engine`에서 관리한다. 기존 네이티브 동작은 같은 공통 코드를 소비하도록 유지한다.
- 사이트 저장소는 `@dmnote/editor`, `@dmnote/web-host`를 버전을 고정해 설치하고 메인 문서와 미리보기 iframe을 조립한다. Cloudflare CSS 중계의 URL 설정과 실제 배포도 사이트 측 책임이다.
- 이번 브랜치에서 웹사이트·Cloudflare 프로젝트 생성이나 공개 배포는 수행하지 않는다. 패키지 소비·브라우저 통합 검증용 화면은 제품 화면과 별도로 둔다.
- 실행 세션의 undo/redo 기록은 메모리에 유지하고 Worker가 재시작되면 비운다. 문서·설정·플러그인 저장·자산·저장 확인 기록은 IndexedDB에서 복원한다. history 메타는 전진시켜 기존 화면의 오래된 관측값이 적용되지 않게 한다.

### D1. 공통 Rust 편집 엔진

- 편집 결과의 검증과 확정에 관한 공통 로직을 Rust로 추출한다.
- 데스크톱은 네이티브 Rust로, 웹은 WebAssembly로 같은 엔진을 사용한다.
- 메인과 오버레이가 각각 독립적인 편집 상태를 확정하지 않는다. 하나의 권위 있는 편집 세션을 사용한다.
- Tauri, 파일 시스템, 윈도우, 네이티브 입력에 의존하는 부분은 환경별 호스트에 둔다.
- 공통 엔진의 책임 범위는 4.4와 같이 확정한다. 앱의 최종 동작과 결과값이 기존과 동일해야 한다는 조건으로 내부 구조 변경을 승인받았다.
- 웹의 Rust/WASM 엔진과 IndexedDB 저장 모듈은 SharedWorker에서 실행한다. 작업·실행 세션·화면을 구분하며 세션별 엔진 상태를 관리한다.
- 구체적인 Rust crate 경계와 호출 계약은 후속 설계에서 정한다. 웹 저장·확정 순서는 4.2를 따른다.

### D2. 공통 UI와 환경별 호스트

- React 편집 UI, 공유 렌더러, 플러그인 런타임과 API 구현을 가능한 한 공유한다.
- 환경별 파일 입출력, 저장, 입력, 통신 기능은 호스트 어댑터로 연결한다.
- 기존 API의 의미와 메인·오버레이 역할을 유지한다. 웹 전용 의미로 공용 API를 다시 정의하지 않는다.

### D3. 저장 모듈 분리

- 공통 엔진의 데이터 처리와 실제 영속 저장 수단을 분리한다.
- 데스크톱은 기존 네이티브 저장 경로를 유지하고, 웹에는 브라우저용 저장 모듈을 둔다.
- 저장 성공·실패와 편집 확정·히스토리·이벤트의 관계는 현재 앱의 의도를 보존한다.
- 웹 저장 수단은 IndexedDB로 한다. 작업 상태·설정·플러그인 데이터와 바이너리 자산을 논리적으로 구분해 저장한다.
- 웹은 변경 준비 → IndexedDB 저장 완료 → 엔진 확정 순서로 연결한다. 앱은 기존 저장 순서와 보장을 유지하며, 공통 엔진 추출에 필요한 코드 분리·재연결은 수행할 수 있다.
- 웹에서 함께 변경되는 문서·설정과 새 자산은 같은 IndexedDB 데이터베이스의 한 쓰기 트랜잭션으로 저장한다. 필수 쓰기 실패 시 전체 작업을 중단한다.
- 세부 스키마, 트랜잭션 및 복구 절차는 후속 설계에서 정한다.

### D4. 프리셋 입출력은 현재 앱과 동일

- 현재 JSON 프리셋 형식을 유지한다.
- 현재 앱이 포함하는 로컬 이미지·폰트·사운드 자산은 JSON 안에 묶어서 내보낸다.
- 가져올 때 내장 자산을 풀어 각 환경에서 사용할 수 있는 저장소와 자산 참조로 연결한다.
- 웹 전용 프리셋 포맷이나 플러그인 상태 포함 규칙을 새로 만들지 않는다.
- 필드 누락과 빈 값의 처리, ID 처리, 기존 상태와의 병합·교체 등은 현재 앱 동작을 기준으로 한다.
- 브라우저의 작업 상태 저장 형식과 사용자에게 내보내는 프리셋 파일 형식은 별개의 책임이다. 내부 저장도 매번 자산을 포함한 JSON 한 덩어리로 해야 한다는 결정은 아니다.

### D5. 플러그인 API와 저장 의미 유지

- `dmn.window.type`의 `main` / `overlay` 구분, 각 컨텍스트의 실행과 생명주기 의미를 유지한다.
- `dmn.plugin.storage`는 앱의 플러그인 저장 API다. 브라우저 `localStorage`와 같은 것으로 취급하지 않는다.
- 플러그인별 저장 이름공간과 기존 저장 동작을 유지하고, 웹에서는 그 뒤의 저장 구현을 교체한다.
- 프리셋에 무엇을 포함할지는 기존 앱 구현을 따른다. 현재 `PresetFile`의 `customJS`와 일반 플러그인 저장 데이터는 구분한다.
- 현재 프리셋에 포함되지 않는 플러그인 인스턴스 저장 데이터나 설정을 웹 이식을 이유로 추가하지 않는다.
- 플러그인을 개별 iframe으로 분리하는 구조는 채택하지 않는다. 실제 DOM, React 요소, 동기 반환과 콜백을 사용하는 기존 계약을 고려한다.

### D6. 메인 화면과 오버레이 미리보기

- 웹의 일반 편집 화면은 `main`, 미리보기는 `overlay` 역할로 연결한다.
- 오버레이 미리보기에는 별도의 iframe 문서를 사용한다. 각 컨텍스트의 플러그인은 해당 문서의 DOM을 사용한다.
- 데스크톱의 윈도우 간 통신은 웹 호스트에서 메인과 미리보기 간 통신으로 대체한다.
- iframe은 문서와 스타일·실행 컨텍스트를 구분하기 위한 선택이다. 이것만으로 악성 플러그인에 대한 보안 격리가 성립한다고 가정하지 않는다.
- 메인 전체나 편집 캔버스를 추가 iframe으로 옮기는 방안은 현재 채택하지 않았다.
- iframe 초기화·재시작, 메시지 순서, 상태 재동기화의 상세 계약은 후속 설계 대상이다.

### D7. 웹 키 입력

- 웹 버전은 브라우저에서 받을 수 있는 키 입력을 사용한다.
- 데스크톱의 전역 키 수집을 웹에서도 구현하는 것을 전제로 하지 않는다.
- 미리보기 포커스와 입력 전달, 포커스 상실 시 눌림 상태 해제는 구현 설계에서 구체화한다.

### D8. CSS 처리와 Cloudflare Workers

- 메인 편집 화면의 사용자 CSS는 현재 스코프 처리 방식을 유지한다.
- 메인의 외부 `@import` 인라인 처리에 필요한 다운로드는 웹에서 Cloudflare Workers로 중계한다. 무료 플랜으로 시작한다.
- 데스크톱은 기존 Rust 다운로드 경로를 유지한다.
- 공통 CSS 처리 코드에는 같은 가져오기 계약을 제공한다. 현재 계약은 URL을 받아 `{ finalUrl, text }`를 반환하는 형태다.
- CSS 분석, 중첩 import 해석, 상대 URL 보정과 스코프 처리는 브라우저의 공통 코드에 남긴다.
- 현재 오버레이·OBS의 원문 CSS 주입 경로와 메인의 import 인라인 경로를 구분한다. 모든 자산 요청이나 플러그인 네트워크 요청을 Worker로 보내는 결정은 아니다.
- Worker는 CSS 다운로드 중계를 담당한다. 편집 엔진이나 사용자 프리셋 저장을 서버로 옮기지 않는다.
- 기존 다운로드 제한과 오류 처리 의도를 반영한다. Cloudflare에서의 구현 가능성과 차이는 구현 시 검증한다.
- 무료 한도로 수용 가능한 실제 규모는 측정 전에는 확정하지 않는다. 한도 초과 시 대응, 캐시와 배포 설정은 후속 설계 대상이다.

근거: [Workers 제한](https://developers.cloudflare.com/workers/platform/limits/), [공식 CORS 중계 예제](https://developers.cloudflare.com/workers/examples/cors-header-proxy/).

### D9. 버전 호환

- 최신 앱 버전을 기준으로 설계한다.
- 과거 호환성과 마이그레이션은 앱과 동일한 정책을 따른다.
- 모든 과거 버전을 영구 지원하는 웹 전용 호환 계층은 전제하지 않는다.

## 3. 책임 배치 개요

| 책임              | 공통 부분                     | 데스크톱 호스트       | 웹 호스트                        |
| ----------------- | ----------------------------- | --------------------- | -------------------------------- |
| 편집 결과         | Rust 검증·확정 로직           | 네이티브 실행         | WASM 실행                        |
| 편집 화면         | React UI·렌더러               | 메인 윈도우           | 메인 페이지                      |
| 오버레이          | 렌더러·플러그인 역할          | 별도 윈도우           | 미리보기 iframe                  |
| 저장              | 데이터 처리·저장 계약         | 기존 저장 모듈        | IndexedDB 저장 모듈              |
| 프리셋            | 기존 형식·포함 의미·변환 로직 | 파일 입출력·로컬 자산 | 파일 선택·다운로드·브라우저 자산 |
| 플러그인          | 런타임·API 의미               | 네이티브 기능 연결    | 브라우저 기능 연결               |
| 입력              | 렌더링에 전달할 입력 계약     | 기존 네이티브 입력    | 브라우저 입력                    |
| 메인 CSS 다운로드 | 가져오기 인터페이스·후처리    | Rust HTTP 다운로드    | Cloudflare Worker 호출           |

이 표는 책임의 방향이며, 최종 패키지 구조나 모든 API의 웹 호환성 검증 완료를 뜻하지 않는다.

### 4.1 IndexedDB 기반 저장

**상태: 확정 (2026-09-08).**

- 웹 저장 모듈의 기본 저장 수단을 IndexedDB로 한다.
- 작업 상태와 설정, 플러그인 저장 데이터, 이미지·폰트·사운드 자산을 논리적으로 구분해 저장한다.
- 자산은 Blob 등 바이너리 값으로 저장하고, 내보내기 시 기존 프리셋 형식에 맞춰 묶는다.
- 이는 저장 수단에 관한 결정이다. object store 스키마, 저장 트랜잭션 범위, 저장 성공의 정의까지 확정하는 것은 아니다.
- 브라우저 저장 용량·삭제 정책을 고려해 실패와 복구를 설계해야 한다. 네이티브 파일 저장과 동일한 영속성을 자동으로 얻는다고 가정하지 않는다.

근거: [IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [브라우저 저장 용량 및 삭제 정책](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

### 4.2 저장 완료 후 편집 확정

**상태: 웹의 처리 순서 확정 (2026-09-08). 앱의 기존 동작과 저장 보장은 유지한다. 공통 엔진 추출에 필요한 앱 코드의 리팩터링까지 금지하는 결정은 아니다.**

현재 앱의 `Store::commit_locked`는 writer 완료를 기다린 후 메모리 상태와 store revision을 공개한다. `commit_editor_transition_locked`는 저장 전에 히스토리 계획을 준비하고, 저장 성공 후 히스토리를 적용하고 확정 이벤트를 구성한다.

웹은 다음 순서로 연결한다.

1. 공통 Rust 엔진이 요청을 검증하고 다음 문서·revision·히스토리 변경 계획을 준비한다. 아직 확정 상태에는 반영하지 않는다.
2. 웹 저장 모듈이 변경을 IndexedDB에 기록하고 트랜잭션 완료를 기다린다. 개별 쓰기 요청의 성공만으로 완료 처리하지 않는다.
3. 저장 성공 후 공통 엔진의 준비된 변경을 확정하고, 히스토리와 확정 이벤트를 반영한다. 저장 이후 새로운 검증 실패가 발생하지 않도록 준비 단계에서 필요한 검증을 마친다.
4. 저장 실패 시 직전 확정 상태·revision·히스토리를 유지하고, 현재 오류 계약에 맞춰 실패를 반환한다.

- 화면의 임시 편집 표시와 엔진의 확정 상태는 구분한다. 저장 대기가 드래그 표시 등 기존 즉각적인 UI 피드백을 막지 않도록 한다.
- 저장을 기다리는 동안 후속 변경이 준비된 상태를 무효화하지 않도록 세션 변경을 순서대로 처리한다. 큐의 범위와 재시도·중복 요청 처리는 이어서 구체화한다.
- 자산과 문서의 트랜잭션 범위는 4.3에서 정한다. 저장 직후 세션 종료 시 복구, 여러 탭의 충돌은 이 순서만으로 해결되었다고 보지 않는다.
- IndexedDB의 트랜잭션 완료와 물리적 디스크 기록의 보장 수준은 구분한다. durability 옵션과 복구 계약은 별도로 검토한다.

근거: `src-tauri/src/state/store.rs`, `src-tauri/src/state/store/editor_commit.rs`, [IndexedDB 트랜잭션 완료](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event), [durability 옵션](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability).

### 4.3 웹 문서와 자산의 원자적 저장

**상태: 확정 (2026-09-08). 웹 저장 모듈에 적용하며 앱의 파일 저장·복구 절차는 유지한다.**

- 문서와 자산을 같은 IndexedDB 데이터베이스의 서로 다른 object store에 둔다.
- 이미지 추가나 프리셋 가져오기처럼 자산과 참조가 함께 바뀌는 작업은 새 자산과 이를 참조하는 문서 및 함께 변경되는 설정을 하나의 쓰기 트랜잭션으로 저장한다.
- 필수 쓰기 하나라도 실패하면 전체 트랜잭션을 중단한다. 새 문서만 저장되거나 일부 새 자산만 남는 부분 적용을 방지한다.
- 파일 읽기·Base64 해제·자산 준비·검증은 트랜잭션 시작 전에 마친다. 열린 트랜잭션 안에서 네트워크 요청이나 다른 장시간 비동기 작업을 기다리지 않는다.
- 위치 변경처럼 자산 내용이 바뀌지 않는 편집은 필요한 문서 데이터만 갱신한다. 매번 모든 자산을 다시 기록하지 않는다.
- 기존 자산 삭제·격리와 히스토리 참조의 보존, 대용량 가져오기 한계는 별도 검토 대상으로 남긴다. 문서에서 참조가 사라졌다는 이유만으로 즉시 자산을 삭제하는 정책을 확정하지 않는다.

근거: [여러 object store를 포함하는 트랜잭션](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction), [트랜잭션 중단과 롤백](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/abort).

### 4.4 공통 Rust 엔진의 책임 범위

**상태: 조건부 승인 (2026-09-09). 앱의 최종 동작과 결과값이 기존과 동일해야 한다. 구현 후 검증을 통과했다는 뜻은 아니다.**

공통 엔진에는 편집 결과의 의미를 결정하는 로직을 모으고, 실제 외부 자원에 접근하는 코드는 호스트에 둔다.

| 공통 Rust 엔진                                            | 환경별 호스트                                       |
| --------------------------------------------------------- | --------------------------------------------------- |
| 편집 문서·연관 데이터의 모델, 검증과 정규화               | Tauri 커맨드 또는 웹 호출 진입점                    |
| 편집 명령 적용, revision과 변경 준비·확정                 | 요청 직렬화와 실제 저장 완료 연결                   |
| undo/redo의 변경 계산과 히스토리 상태 관리                | 네이티브 동기화 수단 또는 웹 세션 실행 수단         |
| 프리셋 해석·생성, 필드 적용 의미, 내장 자산 인코딩·디코딩 | 파일 선택·읽기·쓰기·다운로드, 자산 바이트 제공·보관 |
| 데이터 형식의 마이그레이션·복구 판단                      | 파일 백업·격리·저장소 트랜잭션·복구 실행            |
| 확정 이벤트의 데이터 생성                                 | Tauri 이벤트 또는 브라우저 메시지 전달              |

- 프리셋 변환은 문서 데이터만이 아니라 호스트가 제공한 자산 바이트와 참조 매핑을 이용한다. 네이티브 절대 경로나 브라우저 URL을 공통 엔진이 직접 열지 않는다.
- 파일 경로 등 환경별 표현의 해석과 변환은 호스트에 남긴다. 앱의 기존 저장·복구 트랜잭션 소유권을 단순한 파일 이동 때문에 바꾸지 않는다.
- 히스토리의 논리적 상태와 규칙을 공유한다는 뜻이며, 새로고침 후 undo/redo 기록을 영속 복원하는 기능을 추가한다는 뜻은 아니다.
- 플러그인 실행·React·DOM·CSS 처리는 기존 TypeScript 공통 영역에 남긴다. 공유를 위해 Rust로 다시 작성하지 않는다.
- 데스크톱과 웹에서 같은 입력·기존 상태·자산을 주었을 때 같은 의미의 편집 및 프리셋 결과를 얻도록 검증한다. 호스트별 경로 표현까지 같아야 한다는 뜻은 아니다.
- 정확한 crate 위치·공개 타입·메서드와 데이터 전달 방식은 후속 설계에서 구체화한다. WASM 실행 위치는 4.5의 SharedWorker로 확정했다.

승인 조건과 검증 기준:

- 앱의 내부 모듈 분리와 Tauri·저장 연결 리팩터링은 허용한다. 기존 기능이나 데이터 의미를 변경하는 근거로 이 승인을 사용하지 않는다.
- 동일한 초기 상태와 요청에 대해 편집 결과, undo/redo, 프리셋 입출력, 플러그인 API의 반환·이벤트 의미, 실패 시 상태 및 저장·복구 보장이 기존과 동일해야 한다.
- 비교 가능한 결과값은 직접 비교하고, 생성 ID·환경별 경로처럼 실행마다 달라지는 값은 기존 생성 규칙과 참조 관계가 보존되는지 검증한다. 임의의 필드를 비교에서 제외하지 않는다.
- 기존 계약 테스트와 대표 데이터의 리팩터링 전후 비교로 검증한다. 테스트 통과 전에는 동등성 확보 완료로 기록하지 않는다.
- 실제 동작 차이가 필요한 경우 차이와 이유를 제시하고 별도로 논의한다.

### 4.5 SharedWorker 실행과 세션·화면 분리

**상태: 확정 (2026-09-09). 앱 구조와의 유사성 및 웹 편집의 장기적인 활용성을 고려해 SharedWorker를 선택했다. 앱의 네이티브 실행 구조는 이 항목으로 변경하지 않는다.**

- SharedWorker 안에서 Rust/WASM 엔진과 IndexedDB 저장 모듈을 실행한다. 특정 메인 페이지가 엔진을 소유하는 형태 대신, 화면이 필요한 편집 세션에 연결하는 구조를 사용한다.
- 메인과 미리보기는 같은 편집 세션을 사용한다. 미리보기 iframe이 별도 엔진을 만들지 않는다.
- UI와 플러그인의 DOM·React 처리는 각 문서에 유지한다. Worker에는 직렬화 가능한 데이터 요청과 결과를 전달한다.
- 문서 처리와 프리셋 변환 계산을 UI 실행 스레드에서 분리하는 목적이다. 실제 응답 시간이나 프레임 개선 수치는 측정 전에는 보장하지 않는다.
- Worker 통신은 비동기이므로 요청 식별·순서·오류·재시작 계약이 필요하다. DOM을 반환하는 동기 플러그인 API까지 메시지 호출로 바꾸지 않는다.
- 브라우저의 Web Worker와 외부 CSS를 중계하는 Cloudflare Worker는 역할과 실행 위치가 다르다. 전자는 사용자 브라우저 내부에서 실행된다.
- 여러 브라우저 탭의 저장 충돌 정책, Worker 재시작 시 복구, 자산 전달 비용은 후속 설계에서 다룬다.

근거: [Web Workers 실행과 메시지 통신](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers), [Worker의 IndexedDB 접근](https://developer.mozilla.org/en-US/docs/Web/API/WorkerGlobalScope/indexedDB).

선택 근거:

| 선택지                    | 구조와 장단점                                                                         | 현재 앱과의 관계                                                    |
| ------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 메인 페이지에서 WASM 실행 | 호출 연결은 단순하지만 엔진 계산이 UI 실행 스레드를 사용                              | UI와 백엔드 실행 분리 정도가 줄어듦                                 |
| Dedicated Worker 하나     | 페이지가 소유하는 별도 실행 스레드에 엔진·저장 배치, 메시지 통신 필요                 | 한 편집 페이지와 그 미리보기에 대해 UI와 중앙 엔진의 분리를 재현    |
| SharedWorker 하나         | 같은 origin의 여러 탭·창·iframe이 동일 Worker에 연결 가능, 연결별 세션·수명 관리 필요 | 독립적인 여러 화면이 공통 백엔드에 연결하는 형태까지 보면 가장 유사 |

- 현재 Tauri 앱은 하나의 Rust Core가 여러 WebView의 공통 상태를 관리한다. Worker는 브라우저 내부 실행 스레드이므로 네이티브 Core 프로세스와 수명·프로세스 경계까지 같지는 않다.
- 한 페이지와 그 미리보기만 고려하면 Dedicated Worker도 가능하지만, 별도 창·여러 탭으로의 확장을 고려해 SharedWorker를 채택했다. Dedicated Worker 대체 경로를 별도로 구현하는 결정은 아니다.
- SharedWorker를 선택해도 편집 요청의 직렬화·revision 검증·재시작 복구가 자동으로 해결되지는 않는다.

근거: [Tauri 프로세스 모델](https://v2.tauri.app/concept/process-model/), [SharedWorker](https://developer.mozilla.org/en-US/docs/Web/API/SharedWorker).

확정된 확장 방향과 후속 설계 경계:

- 여기서 여러 탭은 브라우저 탭을 뜻한다. 앱 문서 안의 모드·디자인 탭과 구분한다.
- 저장된 작업, 실행 중인 편집 세션, 연결된 화면을 구분한다. 편집 세션은 현재 문서·revision·히스토리·요청 처리 순서를 소유하고, 화면은 그 세션에 연결하는 클라이언트다.
- 같은 작업을 편집하는 화면과 별도 미리보기 창은 같은 세션에 연결할 수 있다. 서로 다른 작업은 문서·히스토리가 섞이지 않도록 별도 세션으로 둔다.
- SharedWorker를 웹 호스트로 두고 세션별 엔진 상태를 관리한다. SharedWorker 하나를 쓴다는 이유로 모든 브라우저 탭을 같은 문서에 강제로 연결하지 않는다.
- 세션 식별과 메시지 계약은 공통 엔진의 브라우저 독립성을 유지하도록 호스트에서 연결한다. SharedWorker의 전역 객체를 공통 Rust 엔진의 상태 소유자로 직접 사용하지 않는다.
- SharedWorker는 동일 origin 등 브라우저가 허용하는 로컬 범위에서 공유된다. 다른 기기·다른 사용자와의 온라인 공동 편집을 제공하는 선택은 아니다.
- IndexedDB를 함께 사용한다는 것과 실행 세션을 공유한다는 것은 다르다. 저장소만 공유하면 탭별 메모리·히스토리는 따로 남으므로, 동일 작업에 대한 쓰기 소유권을 별도로 조정해야 한다.
- 같은 세션의 여러 편집 화면을 허용할 경우 undo 범위, 선택·뷰포트의 화면별 소유권, 플러그인의 중복 실행과 `main`/`overlay` 메시지 대상, 키 입력 소유권을 먼저 설계한다. SharedWorker를 선택하는 것만으로 이 정책들을 확정하지 않는다.
- 연결이 모두 사라지거나 Worker가 종료된 뒤에는 IndexedDB에서 복원한다. 실행 중인 히스토리의 영속 복원은 별도 정책이며, Worker 수명에 저장 완료를 의존하지 않는다.
- 여러 문서 관리 UI나 다중 편집 기능의 즉시 구현을 승인한 것으로 취급하지 않는다. 우선 실행 세션과 화면의 경계를 설계하고, 기능 범위는 항목별로 논의한다.
- 최초 연결 구성은 현재 앱처럼 한 세션에 메인 하나와 오버레이 하나로 둔다. 추가 화면을 수용할 수 있게 경계를 설계하되, 여러 메인의 동시 편집·플러그인 실행 정책은 별도로 정한다.

### 4.6 기존 OBS IPC shim의 공통화

**상태: 확정 (2026-09-09). 기존 공개 API 의미와 앱·OBS 동작을 유지하면서 shim의 범용 부분을 공유한다. 세부 프로토콜과 복구 절차는 후속 설계 대상이다.**

- 공통 UI·플러그인이 사용하는 API의 호출·반환·이벤트 의미를 유지하고, 호스트 통신 계층에서 앱의 Tauri IPC와 웹의 SharedWorker MessagePort를 연결한다.
- 현재 `src/renderer/api/ipcShim.ts`를 기반으로 콜백·이벤트·요청 연결을 공통화하고 전송 및 환경 정책을 주입한다. 기존 `initIpcShim`과 API 진입점 계약은 유지한다.
- 네이티브 앱은 기존 Tauri 연결을 사용한다. OBS는 공통 shim + WebSocket 연결, 웹 편집기는 공통 shim + SharedWorker MessagePort 연결로 구성한다. 범용 shim에 커맨드별 기능 분기를 쌓지 않는다.
- 웹의 각 화면은 SharedWorker에 연결해 편집 세션과 `main`/`overlay` 역할을 등록한다. 연결마다 내부 클라이언트 식별자를 부여한다.
- 통신용 요청 식별자로 응답을 원래 호출에 연결하고, 확정 이벤트는 해당 세션의 구독 화면에 전달한다. 세션·클라이언트 식별은 등록된 연결과 결합해 다른 작업으로 이벤트가 섞이지 않게 한다.
- 세션·클라이언트·통신 요청 식별자는 내부 전송 정보다. 기존 플러그인 API 인자나 프리셋 포맷에 추가하지 않는다. 통신 요청 식별자와 편집 mutation ID·revision의 기존 의미도 구분한다.
- 플러그인 bridge의 `main`/`overlay` 대상은 같은 세션 안에서 해석한다. 대상 부재와 전달 실패는 기존 앱 의미를 보존하도록 구체화한다.
- DOM 반환·React 렌더링·함수 콜백 등 같은 문서에서 처리해야 하는 API는 문서 내부에서 실행한다. 모든 API 호출을 Worker에 전달하는 설계가 아니다.
- 정확한 메시지 스키마, 응답과 이벤트의 적용 순서, 초기 스냅샷과 구독의 연결, 재시작·중복 요청 계약은 후속 설계 대상이다.

현재 호출 계약 참고: `src/renderer/api/modules/editor/editorApi.ts`의 `get`, `commit`, `onCommitted`.

현재 shim 조사 결과와 분리 지점:

| 현재 구현                                             | 재사용·확장 방향                                                           |
| ----------------------------------------------------- | -------------------------------------------------------------------------- |
| `__TAURI_INTERNALS__` 설치, callback 등록·실행·해제   | 같은 Tauri JS API를 계속 사용할 수 있는 공통 호환 계층                     |
| 이벤트 리스너 등록·해제·dispatch, 요청별 Promise 연결 | 공통화하되 웹 세션의 이벤트 대상·구독 준비 계약 반영                       |
| WebSocket 연결, hello/token/ping, 재연결              | OBS 전송·초기화에 유지, 웹은 MessagePort 연결과 세션 등록                  |
| `convertFileSrc`의 OBS HTTP `/media/` 변환            | 환경별 자산 주소 해석기로 분리, 웹의 동기 주소 해석과 URL 준비는 후속 설계 |
| `obs-overlay` 메타데이터와 `obs:resync`               | OBS 동작 유지, 웹에는 main/overlay 역할과 세션 재동기화 연결               |
| OBS `hello_ack`에서 받은 allowlist                    | OBS 서버의 기존 권한 경계 유지, 웹은 웹 호스트가 지원·허용하는 기능을 정의 |

- OBS 진입점은 shim 설치 후 `dmnoteApi`와 overlay UI를 동적 import한다. 웹의 메인과 미리보기도 API를 사용하기 전에 각 문서의 shim과 호스트 컨텍스트를 준비해야 한다.
- 현재 `plugin:event|emit`와 `emit_to`는 로컬 dispatch로 처리한다. 이 구현을 그대로 웹의 세션 간·화면 간 전달 의미로 간주하지 않고, 실제 API 계약에 맞게 라우팅한다.
- 현재 OBS RPC 응답은 문자열 오류를 `Error`로 변환한다. 웹 편집에서는 오류 code·details·retryable 등 기존 편집 오류 구조를 보존해야 한다.
- 현재 RPC의 10초 타임아웃과 snapshot 내용 폐기 후 `obs:resync` 발행은 OBS 동작이다. 웹 편집에서 응답 지연을 저장 실패로 단정하거나 결과가 불명확한 변경을 무조건 재실행하지 않도록 별도 설계한다.
- shim은 요청을 전달하는 계층이다. SharedWorker의 실제 커맨드 처리, 공통 엔진 호출, IndexedDB 저장과 기능별 브라우저 호스트 구현은 여전히 필요하다.

### 4.7 남은 기술 설계 작업

2026-09-09 기준으로 저장 수단·확정 순서·자산 원자성·공통 엔진 책임·SharedWorker·shim 활용은 확정했다. 아래는 전체 계획의 남은 세부 설계이며, 기존 결정을 다시 승인받는 목록은 아니다. 이번 브랜치에서는 1.1에 따라 공통 모듈 추출과 앱 재연결에 필요한 계약·검증을 우선 구체화하고, 웹 전용 구현·배포는 후속 작업으로 유지한다.

1. **세션 접속·복구**: 최초 접속, 화면 새로고침과 Worker 재시작 구분, 초기 스냅샷과 구독 순서, 저장 응답 유실 시 결과 확인·재시도, 같은 작업에 대한 중복 메인 연결 처리.
2. **저장 스키마·자산 수명**: 문서·설정·플러그인 데이터의 기존 의미와 이름공간을 IndexedDB에 매핑, 자산 참조와 URL 준비·해제, 히스토리·복구를 고려한 자산 정리, 용량 부족과 durability 정책.
3. **호스트 기능별 웹 연결**: API별 브라우저 구현, 실제 네이티브 전용 동작의 처리, 입력·포커스·눌림 해제, 플러그인 생명주기·bridge 라우팅. 현재 앱과의 동등성을 유지할 수 없는 항목은 별도로 논의한다.
4. **모듈과 호출 계약**: 공통 Rust crate·TS 모듈의 배치, WASM 입출력 타입과 자산 전달, 변경 준비·저장·확정 인터페이스, 세션의 요청 직렬화 범위와 오류·이벤트 계약.
5. **배포·업데이트**: 정적 사이트 호스팅, CSS Worker의 요청 제한·캐시·오류, 페이지·SharedWorker·WASM의 버전 일치와 업데이트 시 재연결. 최신 앱 기준이라는 기존 호환 정책을 따른다.
6. **추출 순서·검증**: 앱 동작을 보존하는 분리 순서, OBS 회귀 검증, 앱·웹의 편집·프리셋 결과 비교, 저장 실패·재시작·자산 복구 시나리오와 단계별 완료 조건.

위 항목은 구현 담당자가 조사하고 구체화할 작업 목록이다. 현재 사용자에게 추가 결정을 요청해야 하는 구체적인 쟁점은 확인되지 않았다.

- 재연결 절차, 저장 스키마, 메시지 스키마, 모듈 배치와 검증 순서는 기존 합의 안에서 설계하고 근거를 문서에 남긴다.
- 현재 앱의 동작·데이터 의미·저장 보장을 유지할 수 있는 구현 선택은 별도 승인을 요구하지 않는다.
- 실제 조사에서 기존 동작을 변경해야 하거나, 합의하지 않은 사용자 기능·정책 또는 비용 선택이 필요해지는 경우에만 구체적인 차이와 선택지를 제시한다.
- SharedWorker 확장 가능성에 관한 합의가 미정인 다중 편집 기능의 출시까지 승인한 것은 아니다. 현재 범위를 유지하면서 확장 경계를 설계한다.

### 4.8 후속 논의: 공통 엔진 소스 관리와 배포

**상태: 논의 중 (2026-09-09). 별도 저장소 이전은 필수 후속 작업으로 확정하지 않았다.**

| 선택지                         | 관리상 이점                                                      | 추가 관리 사항                                                              |
| ------------------------------ | ---------------------------------------------------------------- | --------------------------------------------------------------------------- |
| DmNote 저장소 안의 독립 패키지 | 엔진과 앱의 연관 변경·검증을 한 PR에서 수행, 기존 개발 흐름 유지 | 앱 내부 경로 의존을 막는 패키지 경계 검사, 패키지 전용 릴리스               |
| 별도 공통 저장소의 패키지      | 앱·웹과 독립적인 변경 이력·권한·릴리스 관리                      | 엔진 수정과 앱·웹 의존성 갱신을 여러 저장소에서 조율, 로컬 연동과 통합 검증 |

현재 추천은 DmNote 저장소 안에 독립 패키지로 유지하고 웹에서는 배포된 패키지를 소비하는 방식이다. 현재 앱 동작을 기준으로 함께 변경·검증하는 작업이 많을 것으로 예상한다는 판단에 근거하며, 영구적인 저장소 배치를 확정한 것은 아니다.

- 소스 위치와 릴리스 주기를 분리한다. 앱 설치 파일을 배포하지 않아도 엔진 패키지만 배포할 수 있도록 구성한다.
- 앱 버전과 공통 패키지 버전은 별도로 관리하되, Rust·WASM·TypeScript 산출물 간 대응 버전과 소스 커밋을 기록한다. 구체적인 버전 정책은 후속 설계다.
- 앱은 저장소 내부의 명시된 crate·패키지 진입점을 사용하고, 웹은 버전이 고정된 배포 산출물을 사용한다. 웹이 DmNote의 소스 내부 경로를 직접 참조하도록 만들지 않는다.
- 패키지를 실제로 묶어 외부 소비 환경에서 빌드하는 검증을 두어, 로컬 workspace 연결에서만 우연히 동작하는 누락을 찾는다.
- 향후 엔진의 독립적인 개발·릴리스나 외부 소비자가 늘어 저장소 분리의 이점이 커지면, 같은 패키지 계약을 유지한 채 소스 관리 위치를 옮길 수 있다.
- 별도 저장소를 선택해도 Git submodule은 필수가 아니다. Rust crate와 npm 패키지의 의존성 관리 방식과 소스 저장소 배치는 별개로 결정한다.
